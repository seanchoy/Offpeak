# Baseline — before performance work (2026-10-07)

"Before" numbers for the upcoming performance tasks (3.2 transform_itinerary N+1,
3.3 batched coordinate loading, 3.4 chat full-table POI load). Measured before any
of those changes, and before 1.2 / 1.3 touch the itinerary and chat endpoints.

## Environment

| Item | Value |
| --- | --- |
| Server | local `uvicorn app.main:app` (no `--workers`) |
| Database | local PostgreSQL 18.4 (Postgres.app), 198 POIs |
| Python / FastAPI / SQLAlchemy | 3.12.13 / 0.136.3 / 2.0.39 |
| Code | commit `15e97df` + uncommitted changes to `benchmark_endpoints.py` only |
| Query counter | `ENABLE_QUERY_COUNTER=true` (local only; off in production) |
| Script | `python -m benchmarks.benchmark_endpoints` |

Runs: 1 warm-up + 100 requests per non-AI endpoint; 1 warm-up + 5 messages for the AI
planner (each message calls Gemini, so runs are kept small).

Latency is local-only (no network hop to the database) and is only comparable with
later local runs. **Query counts are environment-independent** and are the primary metric.

## Analysis

### Itinerary generation: 3 queries per scheduled stop (N+1)

Counting the stops actually returned:

| POIs sent | Stops scheduled | Queries | 2 + 3 × stops |
| --- | --- | --- | --- |
| 3 | 3 | 11 | 11 |
| 5 | 4 | 14 | 14 |
| 9 | 7 | 29 | 23 (+6) |

Queries grow as **2 + 3 × stops**: `transform_itinerary` issues three lookups per stop
(POI by slug, crowd level, busyness for the day). The extra 6 queries in the 9-POI case are
expected to come from the overflow path's per-POI `load_coordinates` (to verify in 3.3).
Target for 3.2: a constant number of queries regardless of POI count.

### AI planner: latency is LLM-bound

14 queries per message, but the database share of the ~5.3 s is negligible; the time is
spent in Gemini calls. The 3.4 target is the query count (the per-message
`get_all_pois` full-table load), not latency.

## Finding: the current algorithm silently drops POIs

- 5 POIs sent → 4 scheduled (`empire-state-building` dropped)
- 9 POIs sent → 7 scheduled (`empire-state-building`, `rockefeller-center` dropped)
- The response `warning` is `null` in both cases, so the user is never told.

Not fixed here; it is the motivating case for returning explicit infeasibility reasons
(PRD R15) and a reference point for the old-algorithm baseline (5.2).
